# 0007 — Recoverable configuration application

**Status:** accepted (2026-10-30)

## Context

SQLite settings, Mihomo's live configuration and its startup file cannot commit
as one transaction. A process can stop after staging a setting, after Mihomo
accepts a reload, or after replacing the file but before recording completion.
Validating an old accepted file against new desired settings can then prevent
startup. Replacing the startup file before reload also loses the last accepted
configuration when an ordinary apply fails.

The user requested a common recovery protocol instead of repairing each setting
individually. Existing domain-rule coordination owns managed-provider preparation
and startup/reconnect recovery; credential rotation already retains both keys.

## Decision

- The common raw apply owns a serialized lifecycle in every connection mode.
  SQLite remains the desired-settings source. A bounded internal journal and
  synchronous staged mutation commit in the same SQLite transaction.
- `config.yaml` holds the accepted payload; `config.yaml.pending` holds the next
  generated payload. The journal stores the canonical path, previous/candidate
  SHA-256 hashes and their Default validation context, without copying credentials
  or node payloads into another settings row.
- Send the pending payload inline through the existing Mihomo client. Successful
  reload and applicable provider/network checks precede accepted-file replacement.
  Credential confirmation and local apply bookkeeping precede journal removal.
  A failed ordinary apply retains intent; a pending journal forces a real reload
  even when the generated bytes equal the startup file.
- Bootstrap and application startup reject unknown bytes, a missing previously
  accepted file, malformed proof or a different config path. A proven previous
  file is validated in its accepted context while desired settings remain saved.
  A proven candidate already moved to the accepted path also remains pending.
  Offline preparation cannot confirm activation or clear the journal.
  The supported pre-native Proxy migration may generate a prepared candidate from
  desired settings. Rebase the current proven primary identity before publishing
  its replacement, so interruption on either side of rename remains recoverable.
  Native/TUN validation failures do not use this migration exception.
  Preserve any accepted canonical managed rule provider at a REJECT target in its
  normal rule position until the online owner attests the current store and VPN
  route. A missing or unsafe accepted definition blocks migration explicitly;
  managed destinations cannot fall through to a Direct default during preparation.
  Before loading any accepted managed provider, inspect its backing file using the
  existing store safety checks and SQLite digest history. Only the confirmed digest
  or an unfinished operation's intended digest is recoverable. Offline inspection
  does not promote the marker or finish the separate domain-rule operation.
- The existing coordinated boot/first-connect/reconnect owner regenerates from
  current desired settings and current managed rules. It does not blindly replay
  an old provider payload. Pending credential rotation continues to use both keys;
  offline bootstrap preserves a journal-bound file until online apply finishes.
- Explicit rollback callers restore the previous file first, then atomically
  undo their staged mutation and restore the preceding journal. A crash during
  rollback remains an interrupted operation for the same recovery owner.
  If the engine restore reload fails, retain a fresh pending journal bound to the
  restored file so the next apply verifies activation even with identical bytes.

## Consequences

- One protocol covers routes, nodes, channels, connection settings and credential
  config publication. It adds no worker, dependency, generic DB snapshot framework
  or distributed transaction. Existing explicit rollback semantics remain intact.
- Recovery is idempotent for process termination at each publication boundary.
  Tests kill real child processes; isolated Docker qualification also exercises
  the normal application startup against Mihomo.
- A journal and pending artifact are runtime data and belong with the database
  and accepted config in backups. External modification requires explicit repair;
  it is never interpreted as a proven interrupted operation.
- Invalid desired settings can still block an apply. Host storage corruption,
  simultaneous writers and filesystem power-loss guarantees are outside this
  process-recovery protocol. The last accepted config is retained on observed
  activation failure, and failed recovery never claims confirmed activation.
